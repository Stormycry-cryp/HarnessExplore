# Harness 实践练习

按当前模块挑一个练习，不要求全部做完。以下 trace、状态和 JSON 均为虚构教学材料，不是 Codex 协议或实测日志。设计参考见 [一手资料索引](official-sources.md)；不需要付费 API 或部署。

## 1. 把五层边界画清楚

```text
产品：用户目标、领域上下文、业务记录与授权
                    ↓
Harness：调用模型、路由工具、管理本轮状态与反馈
       ↙            ↓              ↘
模型：生成决策    持久 session     工具：业务 API / MCP / 文件操作
                与恢复记录                 ↓
                                  执行环境：进程 / sandbox
```

模型提出 tool call；Harness 检查、路由并回填结果；工具执行动作；sandbox 限制具体执行环境；产品决定业务规则和最终完成条件。一个系统可能合并部署多层，仍需分别检查职责。sandbox 可写不代表业务操作已获授权；完整 session 日志不代表所有历史都进入当前模型上下文。

**检测题**：一个生成图片的产品要增加图层拆分。哪些行为属于业务工具，哪些应保留在通用 Harness？如果工具只返回任务 ID，产品什么时候可以向用户显示完成？要求画出数据、控制和验证的路径。

## 2. 判断 Codex 的集成方式

| 需求 | 当前官方提供的入口 | 要核查的工程产物 |
|---|---|---|
| CI 中执行一次有界任务 | `codex exec` | 输入、退出状态、结构化结果与产物 |
| 应用代码启动、恢复或流式读取任务 | Codex SDK | thread、事件、取消和错误处理 |
| 产品维护持续会话、展示执行事件和响应审批 | Codex app-server | thread/turn 生命周期、事件与审批请求 |
| 将 Harness 的运行交给服务商 | 托管 Agents API | session、工具、执行环境、数据与服务边界 |

前三项在本次 Codex checkout 中查证，托管服务查对应官方文档。不能把托管功能推定为某个开源 commit 已有的行为。课程只做比较，不自动启动这些服务。

**产出**：为自己的产品选一个入口，写明运行方、业务规则所有者、权限来源和两条失败处理要求。

## 3. 从 trace 找到过早完成

任务：修改本地示例应用的导出功能，用户要求点击导出后保存并重新打开文件。

```jsonl
{"step":1,"event":"task_started","task":"export-file"}
{"step":2,"event":"tool_result","tool":"edit","status":"ok"}
{"step":3,"event":"tool_result","tool":"build","exit_code":0}
{"step":4,"event":"assistant_claim","status":"complete"}
```

**先让学习者回答**：已有证据证明了什么？哪些要求仍未验证？增加什么观察最有价值？

答题后再讲评分依据：编辑、构建完成有对应证据；点击、保存到磁盘和重开文件仍未知。补充实际交互、输出文件位置和重开结果。若环境无法执行，报告阻塞并保留未通过状态。独立 evaluator 的判断也须关联这些证据。

最小完成契约：

```yaml
task: export-file
scope: 本地示例应用的导出路径
done:
  - 用户点击导出，文件保存到约定目录
  - 重新打开该文件，内容与预期一致
evidence:
  - interaction_record
  - saved_file
  - reopen_result
stop: 达成上述要求，或遇到无法自行解决的环境条件
```

在真实项目中用实际路径与记录替换字段占位，不能仅凭填写契约标记通过。

## 4. 长任务交接与结果不确定

```yaml
task_id: demo-export-001
status: needs_verification
goal: 保存并重新打开导出文件
completed: 已修改实现，构建通过
evidence: build.log
unknown: 实际点击、保存、重开结果
next: 启动应用，验证导出流程
source_commit: 使用实际源码 SHA
```

交接保存任务范围、已做动作、证据、未知项和下一步。当前上下文、持久日志与磁盘产物分别检查，恢复后先确认外部状态。

**故障题**：工具提交任务后连接断开。业务服务可能已经执行，客户端没有收到回执。直接重试会产生什么问题？应检查原请求 ID、任务状态或已有产物；确认未执行后才按服务契约重试。若查询仍无法确定，保持结果未知，避免新增重复写入。该要求来自业务动作的重复执行风险，需要按真实 API 契约设计。

## 5. 从 badcase 建立最小 eval

把第 3 节故障写成一个可重复的案例，先检查证据，再评分：

```json
{
  "id": "export-build-only",
  "fixture": "修改和构建成功，缺少保存及重开证据",
  "expected": "指出验证缺口，继续验证或报告准确阻塞",
  "checks": {
    "does_not_claim_complete": false,
    "identifies_missing_evidence": false,
    "proposes_relevant_next_step": false
  },
  "evidence_refs": []
}
```

`false` 是未通过的初始值，需要观察 Agent 的实际输出和证据后填写。这个案例检验完成判断；真实导出是否正确还要检查运行结果。

在同一模型、工具、权限、任务集和预算条件下比较原流程与改进流程。记录通过情况、耗时、工具次数、成本、人工干预与评分依据；随机性明显时做重复运行。evaluator 与人工意见不一致时保留分歧，检查 rubric 与证据，不能只接受更高分。

## 6. 模型升级后重新评估复杂度

一次只改一个因素，例如额外提示、强制上下文重置、evaluator 或多 Agent 分工。在同一任务集上比较结果和代价；权限边界与完成要求保持一致。旧模型的故障补偿措施可能已经多余，也可能仍然有效，结论需要当前实验支持。

Capstone 最小完成物：五层边界图、一份完成契约、一条真实 trace、一份恢复交接、一个有证据的 eval 案例，以及一项模型/Harness/产品职责判断。没有条件执行真实项目时可以交模拟练习，并明确尚未取得项目运行验收证据。
